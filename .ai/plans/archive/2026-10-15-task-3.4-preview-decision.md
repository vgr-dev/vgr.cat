## 1. Decision

**Do not build per-PR preview deployments. Record Task 3.4 as an explicit non-goal, with a documented revisit trigger.**

Rejected alternatives:

- **(A) `env.preview` + `wrangler deploy --env preview`** — rejected on *function*, not on risk. It does not do what the task says it does: a Wrangler environment creates a single persistent Worker (`vgr-cat-preview`) that **every** pull request overwrites. Last-write-wins, no per-PR isolation, no per-PR URL, and concurrent PRs race. Cloudflare's own guidance is explicit that environments are for persistent staging/development and that Previews are the tool for "every branch or pull request". Option A also permanently adds a second Worker to the account that nothing else uses.
- **(B) `previews` block + `npx wrangler preview --name pr-<N>`** — technically sound and is the modern, correct mechanism (see Appendix A for its complete, ready-to-implement spec). Rejected *now* on cost/benefit and on a concrete integration blocker (below).

### Why (C), concretely

1. **The feature would not run on the PRs this repository actually receives.** Dependabot is the only realistic source of PRs here (`.github/dependabot.yml`; plan-verified example PR #2 was a Dependabot TypeScript bump). GitHub states plainly: *"Secrets are not available to workflows triggered by Dependabot events"*, and the Dependabot troubleshooting guide tells you to put credentials in *Dependabot secrets rather than GitHub Actions secrets*. So a `pull_request`-triggered `preview.yml` using `${{ secrets.CLOUDFLARE_API_TOKEN }}` would either fail red on every Dependabot PR (bad — it would erode a pipeline that is currently 100 % green and byte-verified) or, with an actor guard, silently skip on essentially every PR (a feature that does nothing). Making it work requires duplicating both Cloudflare credentials into a second secret store — more credential surface and a drift hazard between two copies of the same token, for a preview of a one-page site.
2. **Near-zero decision value at this scale.** The site is one static page with no SSR, no bindings, and no secrets. Dependency bumps do not change rendering, so the preview would show an identical page. The plan's non-goals explicitly exclude content, design, and SSR work — the categories whose review actually benefits from a rendered preview.
3. **An equivalent review path already exists, for free.** `ci.yml` uploads the built `dist/` as a 7-day artifact (~4 KB), and `npm run preview` serves the same output locally on `:4321`. Neither costs a beta dependency or a second config surface.
4. **Beta risk with no compensating upside.** `npx wrangler preview` is flagged `[open beta]` by the pinned CLI. Beta in a *non-production* path has a contained blast radius, so this alone would not have been disqualifying — but it is real maintenance risk (flag/behaviour drift) purchased for no benefit here.
5. **It touches a Phase 2 artifact and the secret model for a feature nobody will use yet.** See §5.
6. **Doing nothing *is* the safest possible answer to the production-safety constraint.** No Cloudflare account state changes, so `vgr.cat` cannot be affected by construction.

### Revisit triggers (any one of these reopens Task 3.4)

- A PR changes rendering, layout, or styling (i.e. the first time a reviewer needs to *see* the result rather than read the diff).
- SSR / on-demand rendering / `@astrojs/content` (or any adapter) is introduced — previews become genuinely valuable, and remaining Previews limitations stop being irrelevant.
- A second contributor is added who cannot build locally.

When a trigger fires, implement **Appendix A** verbatim. Do not resurrect option A.

## 4. Answers to the specific questions

**Q3 — does `cloudflare/wrangler-action@v4` support `command: preview ...`?**
**Yes.** A plain `run: npx wrangler preview` step is **not** required. The action's own `action.yml` documents the `command` input as *"The Wrangler command (along with any arguments) you wish to run… The `preview` command requires Wrangler >= 4.136.3"*, and the action declares `preview-url`, `preview-deployment-url`, `preview-name`, `preview-id`, and `preview-deployment-id` outputs, plus a `gitHubToken` input for creating GitHub Deployments. Note a documentation discrepancy worth knowing: Cloudflare's Previews docs state the floor as Wrangler ≥ 4.135.0, while the action states ≥ 4.136.3. The project pins 4.151.0, which satisfies both.

If a Builder is ever unsure about the pinned action major, verify against the tag rather than guessing:

```bash
curl -s https://raw.githubusercontent.com/cloudflare/wrangler-action/v4/action.yml \
  | grep -A4 '  command:'
```

**Q5 — does the chosen option change Phase 2 artifacts beyond `wrangler.jsonc`, or alter Phase 4 acceptance criteria?**
**Neither.** Option (C) changes no Phase 2 artifact at all — `wrangler.jsonc`, `astro.config.mjs`, `public/_headers`, and `public/robots.txt` are all untouched, so Task 2.3's verified state (dry-run exit 0, no warnings, 8 files read) remains literally true. ## Appendix A — Ready-to-implement spec for the modern mechanism (option B)

**Do not implement until a revisit trigger in §1 fires.** This spec exists so the decision does not throw away the research. It is complete and implementable as written.

### A.1 `wrangler.jsonc` (exact final content)

```jsonc
{
  "name": "vgr-cat",
  "compatibility_date": "2026-10-15",
  "routes": [{ "pattern": "vgr.cat", "custom_domain": true }],
  "preview_urls": true,
  "previews": {},
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page",
  },
  "observability": { "enabled": true },
}
```

Two additions, both required:

- **`"previews": {}`** — the `previews` block is *required* for `wrangler preview`; it may be empty when a Preview needs no separate settings, which is the case here (no `vars`, no bindings, no secrets). `assets` correctly stays at the top level: *"Keep at the top level, even with an `ASSETS` binding. `npx wrangler preview` uploads assets from the branch you are previewing."*
- **`"preview_urls": true`** — must be **explicit**. Production `workers.dev` and Preview `workers.dev` URLs are configured separately, and `preview_urls`' initial value otherwise depends on `workers_dev`. The top-level `routes` key makes `workers_dev` default to `false`, so without this line a Preview could be created with no reachable host. Enabling it on `workers.dev` (rather than a custom domain) is deliberate: Cloudflare automatically adds `X-Robots-Tag: noindex` to `workers.dev` Preview URLs, and it needs no wildcard DNS or certificate — which matters because Task 4.2 deliberately removed a wildcard route.

Two consequences to record when implementing:

1. `preview_urls: true` also enables per-version URLs for production. It does not change responses on `vgr.cat`, but it is the one line whose effect extends beyond previews.
2. It is applied by `wrangler deploy`, not by `wrangler preview`. **Ordering is mandatory**: land this config on `main` first (the `Deploy` workflow applies it), *then* open the PR that the preview workflow runs on. Otherwise the first preview run may report no host enabled.

`workers_dev` is intentionally *not* set — adding `"workers_dev": false` would be an unrelated, observable change (it would disable the existing `vgr-cat.<subdomain>.workers.dev` URL noted in Task 4.1) and is not needed by this feature.

### A.2 `.github/workflows/preview.yml` (exact final content)

```yaml
name: Preview

on:
  pull_request:

permissions:
  contents: read

concurrency:
  group: preview-pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  preview:
    # Fork PRs never receive repository secrets, and Dependabot-triggered runs
    # cannot read Actions secrets either. Skip cleanly instead of failing.
    # If the Cloudflare credentials are also stored as Dependabot secrets, drop
    # the `github.actor` clause to make previews work on Dependabot PRs too.
    if: >-
      github.event.pull_request.head.repo.full_name == github.repository &&
      github.actor != 'dependabot[bot]'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - run: npm run build
      - name: Deploy Preview
        id: preview
        uses: cloudflare/wrangler-action@v4
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: preview --name pr-${{ github.event.pull_request.number }}
      - name: Publish Preview URL
        env:
          PREVIEW_URL: ${{ steps.preview.outputs.preview-url }}
          DEPLOYMENT_URL: ${{ steps.preview.outputs.preview-deployment-url }}
        run: |
          {
            echo "### Cloudflare Preview"
            echo ""
            echo "- Preview URL (always latest): $PREVIEW_URL"
            echo "- Deployment URL (this commit): $DEPLOYMENT_URL"
          } >> "$GITHUB_STEP_SUMMARY"
```

Design notes, each deliberate:

- **`permissions: contents: read`** only. `gitHubToken` is deliberately *not* passed, so no `deployments: write` is needed; the URL is surfaced in the job summary, which is one click from the PR's checks list. Adding a PR comment would require `pull-requests: write` and would still fail on fork PRs (read-only `GITHUB_TOKEN`).
- **`concurrency`** keyed on the PR number with `cancel-in-progress: true`, matching the `ci.yml` idiom. A cancelled run can leave a stale Preview, which the next push overwrites.
- **`wranglerVersion` is omitted**, matching the working `deploy.yml`. After `npm ci`, the lockfile-pinned Wrangler 4.151.0 is present, and the action prefers an existing installation. This keeps `package-lock.json` the single source of truth for the Wrangler version rather than pinning it in two places. If a future implementer prefers belt-and-braces, `wranglerVersion: "4.151.0"` is valid — just keep it in sync.
- **No cleanup job.** A bare `pull_request` trigger excludes `closed`, and Cloudflare auto-evicts the least-recently-used Preview once the per-Worker limit is reached, so `wrangler preview delete` is unnecessary at this repo's PR volume.
- **Do not add production routes to `previews`.** Cloudflare documents that Previews do not take over zone routes, production custom domains, or other production triggers — which is exactly the guarantee that makes this mechanism safe for `vgr.cat`. This is verified documentation, not an assumption.

### A.3 Rejected variant — custom domain Preview URLs

Instead of `preview_urls`, one could serve previews at e.g. `<preview-name>.previews.vgr.cat` via `{"pattern": "previews.vgr.cat", "custom_domain": true, "previews_enabled": true, "enabled": false}`. Rejected: it needs a dedicated hostname plus wildcard DNS and certificate issuance, it does **not** get `X-Robots-Tag: noindex` for free (Cloudflare adds that only to `workers.dev` previews), and it reintroduces wildcard DNS precisely where Task 4.2 chose to eliminate it.

## Appendix B — Option A spec (rejected; recorded for completeness)

`"env": { "preview": { "routes": [] } }` plus `npx wrangler deploy --env preview` in `preview.yml`. `assets` is an *inheritable* key, so `./dist` would carry into the environment; an empty `routes` array is required because route keys are non-inheritable and must otherwise be given explicitly per environment. Even so, this deploys to a **single persistent** Worker (`vgr-cat-preview`) that every PR overwrites, so it fails the task's own stated purpose and adds a permanent second Worker to the account. Not to be implemented.
